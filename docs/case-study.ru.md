# Археология программного обеспечения: как мы пытались оживить CNTK 2.7 для TIBCO Statistica 14

> **Учебный разбор реального случая (work in progress)**  
> Дата фиксации: 4 ноября 2026 года  
> Цель: восстановить старый пример глубокого обучения MNIST в TIBCO Statistica 14, не ломая уже работающую систему.  
> **Актуальный статус на 6 ноября 2026 года:** цепочка Statistica → обучение CNTK CPU-only → Model → Deployment → таблица предсказаний работает. CSV проверен: 10000 строк, 91 ошибка (точность 99,09%), Predicted совпадает с argmax вероятностей во всех строках; суммы вероятностей отличаются от 1 не более чем на 1,19×10⁻⁹. История восстановления сохранена ниже; итоговая проверка — раздел 23.

## 1. Зачем нужен этот кейс

Иногда учебный пример выглядит тривиально: скачать MNIST, подключить модель, запустить обучение. Но это пример из времени, когда программная экосистема была другой. Документация и код сохранились; совместимое бинарное окружение — нет.

Этот кейс показывает не «как за пять минут установить библиотеку», а **как диагностировать и постепенно восстанавливать воспроизводимую цепочку сборки**. Особенно полезно обсудить со студентами роль LLM: помощник ускоряет расследование, но способен уверенно предлагать неверные пути, параметры и версии. Поэтому проверять нужно не красоту объяснения, а **файлы, логи и результаты измеримых тестов**.

### Конечная цель

Запустить штатный узел **Deep Learning Model Building** в **TIBCO Statistica 14.0.0.15** на примере MNIST, для которого старый C#-код вызывает примерно такую инфраструктуру:

- `StatSoft.DataMinerNodes.Model.CNTK.CNTKSupport.ExecuteModel`;
- внешний CNTK CLI (`cntk.exe`) и связанные DLL;
- конфигурацию CNTK на основе `NDLNetworkBuilder`, `Macros.ndl`, `02_Convolution.ndl`, `CNTKTextFormatReader`;
- первоначально — режим **CPU-only** (`deviceId=-1` в подходящих конфигурациях); позже, возможно, GPU.

Это не значит, что любой современный CNTK автоматически совместим со старой конфигурацией: **движок, синтаксис и скрипты примера должны соответствовать друг другу**. В частности, в исходниках CNTK 2.7 не обнаружились ожидаемые старым примером NDL-файлы из исторического каталога MNIST; это отдельная нерешённая задача.

## 3. Этап нулевой: оживление загрузки MNIST в Python

Исходная задача даже не была связана с C++: Python-код из старого узла Statistica не работал на Python 3.14.

Характерные несовместимости старого скрипта:

- `urllib.urlretrieve` — требовался современный импорт `urllib.request.urlretrieve`;
- `numpy.fromstring` для бинарного буфера — лучше использовать `numpy.frombuffer`;
- `np.uint` — устаревшее/неподходящее обозначение типа;
- `map(...)` в Python 3 — итератор, а не индексируемый список.

Мы адаптировали скрипт под Python 3.14, сохранив интеграционные объекты Statistica (`NodeParameters`, `Application.Spreadsheets`, `DownstreamDocument`). **Оба узла подготовки MNIST — train и test — успешно выдали пути к TXT-файлам.**

**Вывод:** ошибка одного языка не доказывает, что сломан весь пакет. Сначала восстанавливаем каждую ступень конвейера независимо.

## 4. Почему загрузка данных заработала, а обучение — нет

Следующий узел, **Deep Learning Model Building**, работал через C# и старый CNTK CLI. В установленной Statistica не оказалось каталога `cntk` с готовыми исполняемыми файлами. Просто обновить Python здесь недостаточно: нужен **отдельный бинарный стек C++**.

Проверили доступные архивы: один ZIP, который выглядел как дистрибутив, оказался **исходным кодом**, а не комплектом `cntk.exe` и DLL. Стало ясно, что предстоит компиляция.

Отсюда первый общий урок: **«найден архив проекта» не означает «найден бинарный релиз проекта»**. Нужно проверить тип архива и наличие нужных артефактов.

## 5. Исходники: ZIP против Git с подмодулями

Первая копия исходников находилась в `C:\CNTK\src`. При попытках сборки выяснилось, что отсутствует проект:

```text
Source\Multiverso\src\Multiverso.vcxproj
```

Причина: ZIP исходников не включал содержимое Git-подмодуля Multiverso.

Перешли на настоящий Git checkout:

```cmd
git clone --branch v2.7 --depth 1 https://github.com/microsoft/CNTK.git git-src
cd /d C:\CNTK\git-src
git submodule update --init Source/Multiverso
git describe --tags --always
```

Последняя команда вернула `v2.7`, а `Multiverso.vcxproj` появился.

**Вывод:** если старый CMake/MSBuild-проект ссылается на несуществующие вложенные каталоги, проверьте **Git submodules**, а не начинайте создавать заглушки и фиктивные проекты.

## 6. Toolchain: новый Visual Studio и старый компилятор

Был установлен **Visual Studio Build Tools 2026**, но для CNTK требовался старый C++ toolset `v141`. Его удалось добавить отдельным компонентом. Мы проверили:

```text
MSBuild.exe:
C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\MSBuild\Current\Bin\MSBuild.exe

vcvarsall.bat:
C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvarsall.bat
```

В `cmd.exe` инициализация выглядела так:

```cmd
call "C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvarsall.bat" x64 -vcvars_ver=14.16
cl
```

`cl` показал версию `19.16.27054`. Это подтвердило **наличие и работоспособность компилятора**, но **не гарантировало** совместимость всех библиотек CNTK.

Исторический `Tools\devInstall\Windows\DevInstall.ps1` мог попытаться установить целый набор старых пакетов (CUDA, cuDNN, Anaconda, MPI, Boost, MKL-DNN, Protobuf, OpenCV). Мы сознательно не запускали автоматическую установку: она могла поменять нежелательные системные компоненты. **Наличие скрипта установки не означает, что он безопасен для современной рабочей машины.**

## 7. MPI и Boost: первый настоящий прорыв

### 7.1. Microsoft MPI

Отдельно установлены MPI SDK и Runtime. Проверены файлы:

```text
C:\Program Files (x86)\Microsoft SDKs\MPI\Include\mpi.h
C:\Program Files (x86)\Microsoft SDKs\MPI\Lib\x64\msmpi.lib
C:\Program Files\Microsoft MPI\Bin\mpiexec.exe
```

Переменные для PowerShell:

```powershell
$env:MSMPI_INC = "${env:ProgramFiles(x86)}\Microsoft SDKs\MPI\Include"
$env:MSMPI_LIB64 = "${env:ProgramFiles(x86)}\Microsoft SDKs\MPI\Lib\x64"
```

**Оговорка:** эти переменные существуют лишь в текущей сессии PowerShell и не переживают перезапуск системы, если их специально не сохранить. Использование MPI здесь обусловлено зависимостями старой сборки; оно не означает, что для локального запуска модели понадобится распределённое обучение.

### 7.2. Boost 1.60 и несовместимый Boost.Build

Исходники Boost 1.60 расположены в:

```text
C:\CNTK\deps\boost_1_60_0
```

`bootstrap.bat` создал `b2.exe`, но попытки сборки сначала падали **до компиляции**:

```text
missing argument global-setup
ERROR: rule "errors.error" unknown in module "msvc"
```

Корень проблемы — очень старый Boost.Build пытался угадать структуру установки Visual Studio, которой тогда ещё не существовало.

**Что не сработало:** простая передача `toolset=msvc-14.1`; затем прямой путь к `cl.exe` без настройки setup-скрипта. Ошибки изменялись, но сборка не начиналась.

**Что сработало:** указать компилятор явно, задать `vcvarsall.bat` и отключить переписывание setup-скриптов. Рабочий `project-config.jam`:

```jam
import option ;

using msvc : 14.0 :
    "C:/Program Files (x86)/Microsoft Visual Studio/18/BuildTools/VC/Tools/MSVC/14.16.27023/bin/HostX64/x64/cl.exe" :
    <setup>"C:/Program Files (x86)/Microsoft Visual Studio/18/BuildTools/VC/Auxiliary/Build/vcvarsall.bat"
    <rewrite-setup-scripts>off
    ;

option.set keep-going : false ;
```

Здесь `14.0` — **идентификатор для старого Boost.Build**, а реальный компилятор из каталога `14.16.27023` — **v141**. Поэтому выходные библиотеки называются `...vc140...`. Такое расхождение может вызвать **позднейшие проблемы автолинковки**, и его ещё предстоит проверять; нельзя просто объявить любую компоновку безопасной.

Мы сначала проверили одну небольшую библиотеку:

```cmd
b2.exe toolset=msvc-14.0 address-model=64 architecture=x86 variant=release link=static threading=multi runtime-link=shared --with-system --stagedir=stage stage -j2
```

Результат:

```text
compile-c-c++ ... error_code.obj
msvc.archive ... libboost_system-vc140-mt-1_60.lib
common.copy stage\lib\libboost_system-vc140-mt-1_60.lib
...updated 13 targets...
```

Появилось предупреждение:

```text
Unknown compiler version - please run the configure tests and report the results
```

Однако **статическая библиотека фактически была скомпилирована и создана**. Это предупреждение не равнозначно успешной полной совместимости всех компонентов.

Затем собрали почти весь нужный Boost (без Python, MPI и ряда необязательных модулей):

```cmd
b2.exe toolset=msvc-14.0 address-model=64 architecture=x86 variant=release link=static threading=multi runtime-link=shared --without-python --without-mpi --without-context --without-coroutine --without-coroutine2 --without-graph_parallel --without-test --without-wave --stagedir=stage stage -j2
```

Итог:

```text
...updated 495 targets...
27 файлов *.lib, всего 165 583 864 байт
```

Среди результатов — `boost_system`, `boost_filesystem`, `boost_program_options`, `boost_regex`, `boost_thread` и другие. Проверка `Test-Path` для заголовков и библиотек дала `True`.

**Вывод:** при сложных сборках сначала добейтесь появления **одного проверяемого артефакта**, а только потом расширяйте сборку. Не смешивайте все 20 проблем в один огромный лог.

## 8. MSBuild: три разных класса ошибок

### Ошибка № 1. Сборка `.sln` с неверной целью

Мы запустили MSBuild решения с `/t:CNTK` и получили десятки ошибок:

```text
MSB4057: в проекте нет целевого объекта "CNTK"
```

Кроме того, обработались тестовые C# проекты и потребовали `Microsoft.NET.Sdk`:

```text
MSB4236: не удалось найти указанный пакет SDK "Microsoft.NET.Sdk"
```

**Наша ошибка в плане:** мы предположили, что цель `CNTK` решения будет корректно применена, но она попала и в проекты, у которых такой цели нет. А тестовый `.NET SDK` не является обязательным условием для целевой задачи `cntk.exe`.

**Исправление:** запускать непосредственно `Source\CNTK\CNTK.vcxproj`, с `/t:Build` и явным `/p:SolutionDir=...`. Однако это не делает внутренние библиотеки готовыми автоматически.

### Ошибка № 2. Сгенерированный заголовок `buildinfo.h`

При прямой сборке исполняемого файла C++ компиляция остановилась на:

```text
fatal error C1083: Cannot open include file: 'buildinfo.h'
```

Поиск по реальным исходникам нашёл:

```text
Source\CNTKv2LibraryDll\prebuild.bat
```

Скрипт содержит комментарий о генерации `Generated\Windows\buildinfo.h`. После работы с механизмом генерации последующая попытка сборки прошла этот участок. **Это следует из исчезновения ошибки и перехода к стадии `LINK`; содержимое самого заголовка в разговоре отдельно не было продемонстрировано**, поэтому не стоит придумывать точный список его макросов.

**Вывод:** прежде чем вручную сочинять отсутствующий `.h`, ищите `PreBuildEvent`, `Generated`, `*.bat`, `*.props`, `*.targets` и правила генерации.

### Ошибка № 3. Компоновщик не находит `.lib`

После прохождения компиляции `CNTK.exe` сборка дошла до:

```text
LINK : fatal error LNK1181
```

Само сообщение о названии отсутствующего файла в журнале было пустым/неинформативным. Но полная команда `link.exe` показала перечень библиотек:

```text
Cntk.Core-2.7.lib
Cntk.Actions-2.7.lib
Cntk.SGD-2.7.lib
Cntk.ComputationNetwork-2.7.lib
Cntk.Math-2.7.lib
Cntk.Common-2.7.lib
Cntk.SequenceTrainingLib-2.7.lib
Cntk.PerformanceProfiler-2.7.lib
```

В выходной папке ещё не было ни одной такой `.lib`. **Отсутствие внутренних библиотек — обоснованное объяснение провала линковки, но конкретный первый недоступный файл по `LNK1181` достоверно не установлен.**

Мы переключились на сборку библиотек по одной. Первая:

```text
Source\Common\Common.vcxproj
```

**Успешный результат:**

```text
C:\CNTK\git-src\x64\Release_CpuOnly\Cntk.Common-2.7.lib
32 936 158 байт
```

Ошибок в `common_build.log` не обнаружено.

**Вывод:** компиляция исходников приложения не означает готового приложения. Отделяйте **prebuild**, **compile**, **archive**, **link** и **runtime**.

## 9. Где мы остановились: библиотека Math требует Intel MKL

Следующей попытались собрать:

```text
Source\Math\Math.vcxproj
```

Сборка остановилась на штатной проверке:

```text
Math.vcxproj(235,5): error : MKL location not specified
```

В самом `Math.vcxproj` найдена точная логика:

```xml
<Error Condition="'$(MathLibrary)' == 'MKL' And '$(MKL_PATH)' == ''"
       Text="MKL location not specified, ..." />
```

Это **факт из локального файла**: для выбранной математической библиотеки `MKL` требуется свойство MSBuild **`MKL_PATH`**. Ранний совет LLM использовать только `CNTK_MKL_PATH` оказался непроверенным и недостаточным.

По дальнейшему анализу настроек в ходе беседы предполагалась схема с **MKLML** (`mklml.lib`, `mklml.dll`, заголовки Intel MKL), но **архив ещё не скачан, структура не проверена, совместимость конкретной версии не подтверждена**. Не утверждайте, что установка уже выполнена.

Далее нужно исследовать `CNTK.Cpp.props`, свойства `MathLibrary`, `MathIncludePath`, `MathLibraryPath`, `MathLinkLibrary`, фактически установить совместимую библиотеку и только затем повторять `Math.vcxproj`.

**Контрольный критерий:** `Math.vcxproj` должен завершиться кодом `0`, а в выходном каталоге появиться ожидаемый `.lib` и связанные DLL; одного исчезновения сообщения `MKL_PATH` мало.

## 10. Ошибки, которые допустил LLM: разбираем публично

Этот раздел особенно важен для обучения.

| Предложение / гипотеза | Что показал опыт | Как было лучше |
|---|---|---|
| `boost` сам найдёт свежую Visual Studio | Не нашёл, ошибки в старом `msvc.jam` | Сразу проверить связку **версия Boost.Build ↔ версия MSVC ↔ пути** |
| Задать `msvc-14.1` | В Boost 1.60 настройка ломалась | Пробовать минимальный тест с явными `cl.exe` и setup-скриптом |
| Прямой путь к `cl.exe` достаточен | Снова `missing argument global-setup` | Задать `<setup>` и `<rewrite-setup-scripts>off` |
| Собирать решение с `/t:CNTK` | Много `MSB4057`, задевало C# тесты | Сначала исследовать действительные targets/projects |
| Использовать предполагаемые пути к проектам `Math`, `SGD`, `Actions` | `Math.vcxproj` действительно найден; остальные пути **ещё не проверены** | Всегда `Test-Path` перед запуском, лучше извлекать проекты из `.sln` |
| Утверждать детали `buildinfo.h` до проверки содержимого | Генератор найден, но точные макросы не проверялись | Проверять фактический результат генерации |
| Предлагать `CNTK_MKL_PATH` как достаточную переменную | `Math.vcxproj` требует `MKL_PATH` | Читать условие `<Error>` в исходном `.vcxproj` |
| Предлагать MKL/MKLML до проверки точной версии и каталога | Пока нет установленной библиотеки | Сначала проверить `.props`, архив, структуру и лицензирование |
| Делать вывод, что `LNK1181` точно указывает на определённую `.lib` | В журнале имя первого файла отсутствует | Смотреть команду `link.exe`, выходной каталог, dependency graph |
| Разбивать PowerShell-команду через обратный апостроф | При копировании часть продолжений пропала; `/p:` стал отдельной командой | Предпочесть массив аргументов с splatting `& $msbuild @buildArgs` |

**Главный урок:** LLM полезен не потому, что не ошибается, а потому, что с его помощью можно быстро строить и проверять гипотезы. Но в процессе надо регулярно говорить: **«Что именно доказано логом? Что лишь предположено?»**

## 11. Методика восстановления легаси-систем: алгоритм для студентов

1. **Опишите успех наблюдаемым образом.** Не «CNTK вроде установлен», а «`cntk.exe` запускается, читает нужный NDL/CNTK-конфиг, проходит одну эпоху MNIST из Statistica».
2. **Зафиксируйте неизменяемые ограничения.** Версии приложения, Python, ОС, корпоративные ограничения, доступный компилятор, CPU/GPU.
3. **Создайте карту зависимостей.** Что вызывает что: Statistica → C# node → CLI → C++ библиотеки → BLAS/MKL, MPI и т. п.
4. **Установите источник истины.** Приоритет: локальный текст ошибки → `.vcxproj` / `.props` / `.sln` → содержимое архива → официальные старые инструкции → догадки LLM.
5. **Разделите окружения.** Исходники и зависимости в отдельной папке; никаких случайных замен системного Python.
6. **Проверяйте один слой за раз.** Git checkout и submodules → toolchain → headers → одна библиотека → набор библиотек → link → запуск.
7. **После каждого сбоя сохраняйте полную команду и точную ошибку.** Код возврата, путь проекта, конфигурация, лог.
8. **Не делайте «исправлений для красоты».** Не удаляйте проверки, не создавайте пустые заголовки, не переименовывайте DLL и `.lib` без понимания ABI.
9. **Выбирайте минимальный работающий сценарий.** В нашем случае CPU-only и одна эпоха вместо GPU и длинного обучения.
10. **Отдельно тестируйте интеграцию.** Работающий `cntk.exe` ещё не гарантирует, что старый C# узел Statistica правильно передаст пути, конфиг и примет результаты.
11. **Сохраняйте рецепт и контрольные суммы.** Версии, источники архивов, хеши SHA-256, команды, параметры, дату, ожидаемые файлы.
12. **Разбирайте провалы, а не только победы.** Именно неудачные гипотезы показывают диагностическую методику.

### Как правильно ставить LLM диагностическую задачу

Вместо «почини CNTK»:

Не предлагай переустановку или удаление без необходимости.

## 14. Что ещё могло пойти не так (и почему честно говорить об этом)

Даже успешная компиляция всех библиотек ещё не гарантирует запуска. Возможны:

- несовместимость статических библиотек Boost с автолинковкой (`vc140` в имени и фактический MSVC v141);
- отсутствующие или несовместимые DLL времени выполнения;
- рассогласование версий MKLML, OpenMP и CPU-инструкций;
- дополнительные зависимости Protobuf, OpenCV, zlib и других компонентов;
- отличие синтаксиса конфигурации NDL старого Statistica-примера от поддерживаемого CNTK 2.7;
- проблемы путей, кодировок, лицензий и прав доступа на рабочей машине;
- несовместимость старого CUDA-стека с современными GPU (поэтому сначала CPU-only).

Каждый пункт — **потенциальный риск**, а не уже установленная причина конкретного сбоя.

### Итоговая мысль

**Легаси-разработка — это не столько программирование, сколько экспериментальная археология зависимостей.** Выдвигаем гипотезу, добываем свидетельство из исходников, проводим минимальный эксперимент, сохраняем артефакты, записываем результат и только потом двигаемся дальше.

LLM здесь — ускоритель поиска и формулирования проверок, **не источник окончательной истины**. Наш кейс это особенно хорошо демонстрирует: после нескольких неверных гипотез мы добились реального результата, но не стали выдавать незавершённую сборку CNTK за победу.

### 17.2. Доступный архив не обязательно содержит комплект разработки

Исторический Azure-адрес пакета MKL вернул `AuthorizationFailure`. Это установлено ответом сервера, но не доказывает физическое удаление файла. Повторение той же загрузки не решало проблему доступа.

Далее проверили два неподходящих для непосредственной сборки архива:

- `CNTK.Deps.MKL 2.7.0` из NuGet содержал только DLL: `mklml.dll`, `mkldnn.dll`, `libiomp5md.dll`. Для запуска это полезно, но для компиляции и линковки недостаточно.
- `oneDNN-0.14.zip` содержал исходники MKL-DNN. В нём не было нужного комплекта MKLML, зато `scripts/prepare_mkl.bat` указал точный Windows-пакет `mklml_win_2018.0.3.20180406.zip`.

Последний архив содержал заголовки `mkl_cblas.h`, `mkl_lapacke.h`, `mkl_service.h`, `mkl_vml.h`, импортную библиотеку `mklml.lib` и DLL. Его использование подтвердили успешная сборка Math и последующее обучение. Это подтверждение конкретной конфигурации, а не универсальная гарантия совместимости всех режимов CNTK.

SHA-256 скачанного MKLML: `A584A5BF1C8D2AD70B90D12B52652030E9A338217719064FDB84B7AD0D693694`. Это локально вычисленный отпечаток; он не сверялся с независимым эталоном. Его нельзя сравнивать с хешем другого исторического пакета `mklml-mkldnn-0.12.zip`.

**Урок:** различайте исходники, комплект для разработки и библиотеки для запуска. Проверяйте состав ZIP до установки. Скрипт загрузки внутри исходников иногда полезнее недоступной старой страницы документации.

### 17.3. Код возврата 0 может означать «сборка пропущена»

Первый запуск Core завершился кодом 0, но выдал предупреждение о Protocol Buffers. В проекте цель `Build` имеет условие `HasProtobuf`: без зависимости реальной сборки не произошло. `Cntk.Core-2.7.dll` не появилась.

Поэтому проверка скрипта должна включать три условия: команда завершилась успешно, выполнена нужная стадия, создан ожидаемый результат. Простая проверка существования файла тоже недостаточна, если в каталоге лежит старая DLL: при повторных изменениях нужно учитывать время, лог или контрольную сумму артефакта.

**Урок:** код возврата — часть доказательства, а не всё доказательство. Отсутствующая зависимость может быть оформлена автором проекта как предупреждение и условный пропуск.

### 17.4. Восстанавливать нужно параметры сборки зависимости

Штатный `buildProtoVS17.bat` CNTK указал Protobuf 3.1.0 и `protobuf_MSVC_STATIC_RUNTIME=OFF`. Мы сохранили эту схему: x64, toolset v141, Release, статическая библиотека Protobuf с динамическим CRT `/MD`. Это разные настройки: статическая `.lib` не требует обязательного `/MT`.

Подготовленный `build-protobuf.cmd` создал `libprotobuf.lib`, заголовки и `protoc.exe`; версия компилятора схем проверена командой `protoc --version` — `libprotoc 3.1.0`. **Урок:** согласовывайте архитектуру, CRT, конфигурацию и версию генератора кода с потребителем. Современная последняя версия библиотеки не является автоматической заменой исторической.

### 17.6. «Библиотека есть» и «линковщик её видит» — разные факты

Core скомпилировалась, затем остановилась на `LNK1181` с пустым именем файла. Полная команда `link.exe` показала зависимость `Cntk.Reader-2.7.lib`, которой ещё не было. После сборки Reader ошибка сохранилась: в путях линковщика отсутствовал наш `build/out`.

Раннее добавление каталога в `$env:LIB` оказалось недостаточным. Рабочее исправление — подключить локальный `workspace-link.targets` через поддерживаемое свойство `ForceImportAfterCppTargets`. В нём `AdditionalLibraryDirectories` дополнено `$(OutDir)` с сохранением унаследованных путей. Включён `/VERBOSE:LIB` для диагностики. После этого Core успешно слинковалась.

Важно: при пустом тексте `LNK1181` мы не установили имя первого файла, который вызвал ошибку. Достоверно установлены две отдельные проблемы: отсутствие Reader и отсутствие выходного каталога в явных путях поиска. Их устранение позволило завершить линковку.

**Урок:** проверяйте полную команду инструмента, а не только намерение скрипта. Исправляйте отдельно создание зависимости и путь поиска. Сохраняйте объектные файлы: повторная линковка не требует повторять всю компиляцию.

### 19.1. Ошибка comtypes относится к запуску узла, а не к MNIST

В начале переписки обсуждалась ошибка импорта `comtypes`, необходимого для интеграции Statistica с Python. Это слой до выполнения пользовательского загрузчика. Диагностика должна отдельно проверять интерпретатор, импорт пакета, COM и выполнение кода непосредственно внутри Python Node.

Успешный `pip install` в одном Python не доказывает, что Statistica запускает тот же интерпретатор. Полезно фиксировать `sys.executable`, `sys.version`, путь `comtypes.__file__` и разрядность именно в контексте узла. Внешний тест COM проверяет отдельный слой и не гарантирует успех интеграции приложения.

Ранний совет перейти на Python 3.8 был преждевременным: пользователь явно выбрал сохранение Python 3.14.3, после чего загрузочные узлы заработали по результатам сеанса. При этом архив не позволяет точно установить, какая конкретно установка пакета или настройка устранила первоначальную ошибку. Не следует превращать перечень предложенных действий в перечень доказанно выполненных действий.

**Урок:** отсутствие подтверждения официальной поддержки версии не доказывает невозможность конкретного рабочего сценария. Проверяйте нужную операцию в текущем окружении до предложения сменить интерпретатор.

### 19.2. Миграция Python включала исправление бинарного формата и временных файлов

Старый код читал magic number через `struct.unpack('I', ...)`, то есть с порядком байтов платформы, и сравнивал с перевёрнутыми константами. В предложенном обновлении заголовок IDX разбирается явно как big-endian: `>IIII` для изображений, `>II` для меток. Ожидаемые значения magic — 2051 и 2049.

Дополнительные проверки из диалога, которые стоит сохранить при дальнейшем сопровождении загрузчика:

- длина заголовка не меньше 16 байт у изображений и 8 у меток;
- число записей соответствует выбранной паре train/test;
- размеры изображения равны 28×28;
- длина полезных данных равна `count * rows * cols` либо `count` для меток;
- метки лежат в диапазоне 0–9;
- каждая строка TXT содержит 10 значений one-hot-метки и 784 признака.

Исходное `tempDirectory + 'delete.me'` не добавляло разделитель пути и использовало одно имя для загрузок. Предложенный `TemporaryDirectory` и построение пути через `Path` устраняют этот источник конфликтов. Выходной `NamedTemporaryFile(delete=False)` закрывался до повторного открытия для записи, что существенно при работе с файлами на Windows. Итоговый TXT должен жить достаточно долго для следующего узла; временность загрузочного GZIP и срок жизни результата — разные требования.

**Урок:** переписывание под Python 3 — это не только замена импортов. Нужно сохранить контракт формата, проверить порядок байтов, размеры и жизненный цикл файлов.

### 19.3. Выход Python-узла — таблица с путём, а не таблица пикселей

Исходный код создаёт таблицу 1×2: в первой ячейке `Data File Path`, во второй путь к TXT, затем присваивает её `DownstreamDocument.DataSource`. C#-узел читает этот путь через `InputContainer[0].DataSource.Text(1,2)`.

В ответе веб-модели после скриншотов приведены два исторических пути: `%LOCALAPPDATA%\Temp\mnist_g0bs86de.txt` для train и `%LOCALAPPDATA%\Temp\mnist_no8c6sk4.txt` для test (в ответе использован короткий пользовательский путь `USER~1`). Это ориентиры прошлого сеанса, а не доказательство, что файлы существуют сегодня. До интеграции проверяем актуальные выходные таблицы, существование TXT и количество строк. Для повторяемых занятий предпочтителен явно заданный `dataFilePathToSave` в постоянном каталоге.

**Урок:** при миграции сохраняйте не только содержимое файла, но и форму обмена между узлами: размер таблицы, ячейку пути и объект передачи результата.

### 19.4. C#-код обучения уже есть: повторно запрашивать его было необязательно

| Этап | Поведение исходного узла |
|---|---|
| Рабочие результаты | `RootDirectoryPath`, при пустом значении — системный Temp |

Следовательно, критерий успеха шире обучения: отчёт должен содержать путь, файл должен читаться, сериализация и создание следующего узла должны завершиться. Потенциальные слабые места парсинга видны в самом коде: `LastIndexOf` проверяется через `> 0`, поэтому маркер в начале текста не принимается; конец пути ищется только через `\r\n`; индекс отчёта `[1]` предполагается существующим. Это направления будущей проверки, а не уже доказанные ошибки текущего запуска. Полного кода Deployment в прочитанных фрагментах пользовательского кода нет: его ещё нужно получить или найти локально.
